## 0. 摘要

两个项目不在一个量级：参考页是 256×176×256 的**单屏静态小世界**（一次生成、一张全世界阴影图、相机被锁在 320 格以内），本项目是**全国尺度、流式区块、三级 LOD、级联阴影**的地图。所以"整套搬过来"没有意义，能借的是**它在小尺度上把观感做对的那些具体手法**。

读完源码，值得借的有 9 条，其中 4 条小改动就能出效果：

## 1. 参考页概览

### 1.1 它是什么

一座"梯田山城 + 七层宝塔"的体素场景：山脊上宝塔、山下带围墙的层层城池、河流瀑布、湖、晨昼暮夜循环。每个种子（`?seed=N`）挑一套构图（`pickSite`：宝塔位置、山谷轴向、山块起伏、河道走向、湖、城池外轮廓）。

### 1.2 渲染架构（读源码所得）

| 项 | 做法 | 源码 |
|---|---|---|
| 世界 | `Uint8Array` 256×176×256，单位方块 1 格 | L166 |
| 近景 | 只有暴露面的方块才进实例；按（类别 × 96×96 区块）分块的 `InstancedMesh` | L1812–1884 |

## 2. 光照系统

### 2.1 参考页的做法

**一条曲线驱动一切**（L2252）：太阳高度角 `e`。天空色、雾色、太阳色、半球光、灯笼点亮、时辰标签全部读它。

**太阳轨迹**（L2268–2271）
```js
const a = (tod - 0.25) * 2π
const sa = sin(a) * 0.94
sunDir = ( cos(a)*0.92,  sign(sa)*|sa|^1.6*0.98,  0.14 + 1.0*(1-|sin a|) ).normalize()
```
- 高度取 `|sin|^1.6`：太阳在低角度**停留更久**，金色时刻和黄昏看得清。
- `z` 分量在低角度时偏向南：**低太阳从侧面照亮宝塔，而不是迎着镜头照**（源码注释原话）。

**关键值**（L2275–2306，`e` = 太阳高度，`golden` = 日出日落附近 0..1）

| 量 | 公式 | 正午 (e≈0.9) | 金色时刻 (e≈0.06) |
|---|---|---|---|
| 太阳强度 | `3.6·√smooth(-0.06,0.24,e)·(1+0.55·golden)` | 3.6 | ≈ 3.3 |
| 半球光强度 | `π·(0.27+0.4·smooth(-0.2,0.5,e)+0.2·night+0.2·golden)·(1-0.15·golden)` | ≈ 2.1 | ≈ 1.6 |
| 太阳:天光比 | | ≈ 1.7 | ≈ 2.1 |
| 曝光 | `1 + 0.12·golden + 0.15·night` | 1.0 | 1.12 |
| 雾密度（FogExp2） | `0.0016 + 0.0009·晨昏项 − 0.0011·golden` | 0.0016 | ≈ 0.0014（金色带外的上午最浓，≈ 0.0021） |

**三个不显眼但关键的手法**

1. **照地的光 ≠ 天上的太阳**（L2288–2291）：
   - 地平线附近，照地的光比真实太阳**抬高 0.11**（`_ld.y = max(_ld.y + 0.11*smooth(-0.03,0.05,e)*smooth(0.3,0.1,e), 0.03)`）。注释原话："一道掠射的光会让梯田落进山体和彼此的阴影里。" 日轮仍画在真实位置。
   - 夜里，**看得见的月亮**在北面天空（东北到西北、高约 25°），**照地的月光**却放在山谷一侧、镜头肩后（`kx,0.62,kz`，`kz>0`）——"镜头看到的面才吃得到光"。
   - 太阳→月亮的交接是一盏光的**方向、颜色、强度同时渐变**（`m = smooth(0.06,-0.1,e)`），没有跳变。
2. **暖主光 + 冷阴影**（L2295–2297）：半球光颜色 = 天顶色向冷蓝 `0x8fb0e8` 靠 55–80%；金色时刻再向 `SHADE_DUSK 0x9c8ee0`（偏紫）靠 75%；地面色 `GROUND_DAY → GROUND_DUSK → GROUND_NIGHT`。
3. **雾色 = 背景色 = 天空地平线色**（L2298）：`scene.background`、`fog.color` 和天空穹顶的 `uHorizon` 是同一个值，所以地平线没有接缝，远山逐层淡入天空。

**顶点 AO**（L1855–1861）：只看方块**上一层**的 9 格，`ao = max(0.62, 1 − 0.038·occ)`。廉价，但对体素台阶足够。

**阴影参数**：`bias −0.0006`、`normalBias 0.55`、PCF；远景环、云、水面不投影（L1876、2027）。

**夜灯**（L2098–2154、2236–2243、1606–1611）：六盏点光只在宝塔周围（强度 420，按 `ramp` 渐入渐出，白天 `visible=false` 让着色器跳过）；每盏灯笼/窗一个加性叠加的"光球"立方体，片元着色器沿视线积分软球体；近镜头时收缩变暗、远处保持全尺寸；灯笼按**离宝塔的距离依次点亮**（`uSeq` 扫描，6.5 秒扫完）；周围方块顶点预烘焙 `aLit`（量, 点亮延迟）。

### 2.3 差异与可借鉴点

#### L-1【P0】夜间主光挪到镜头肩后

**问题（推断）**：默认镜头在目标南面朝北看（`CameraPose.ts:3`，`yaw 0 = 镜头在南`；`+z` = 南）。`MOON = [0.4,0.5,-0.6]` 意味着夜间主光**从东北高处来**，朝镜头的面（法线朝南，`n.z>0`）`L = (0.4, 0.5, −0.6)` 而 `n.z > 0`，`N·L` 的 z 项为负，只剩仰角那一份对朝上的面有贡献 → 朝镜头的竖直面基本背光。
`doc/lighting/p0-shots/p2-night-t02b-…jpg`（庐山夜景）里，朝镜头的崖壁是深蓝近黑、只有顶面被照亮，与推断相符。参考页正是为此把"看得见的月亮"和"照地的月光"分开的。

**改法**（三处）：
```ts
// TimeOfDaySystem.ts：紧跟 MOON 常量
/** 夜里照地的月光：放在镜头肩后（南、偏东、中高角），朝镜头的面才吃得到光。日轮/月盘仍用 MOON，不动 */
export const MOON_KEY = new THREE.Vector3(0.28, 0.62, 0.55).normalize()

// EnvironmentManager.ts:98
this.lightDir.copy(L.sunDir).lerp(MOON_KEY, moonK)   // 原来是 L.moonDir
```
- `SkySystem` 继续吃 `L.moonDir`，月盘位置不变。
- 补光 `fill` 位置是 `focus − lightDir·400`（`EnvironmentManager.ts:131`），会自动翻到北侧，天光两侧都不死黑，不用另改。
- **风险**：月盘在北、月光从南来，方向"不一致"。参考页同样如此，且夜里没人会核对；若担心，可把月盘也略向东南挪，但 `SkySystem.ts:93` 注释明确"月亮贴地平 9°，俯看时才看得见"，**不要动**（Phase 0 报告 §3 候选 3 与任务书第 17 条）。
- **验证**：同机位（`shp=lushan&shm=night`）改前改后各一张；重点看朝镜头崖壁与屋墙的亮度。

#### L-2【P0】低角度主光抬升

`EnvironmentManager.update()` 里 `lightDir` 算出来之后、写入 `u.uSunDir` 之前加：
```ts
import { smoothstep } from '../../utils/math'   // 注意：这是 (e0,e1,x)，支持反向边界，与 THREE.MathUtils.smoothstep(x,min,max) 参数顺序不同
const lift = 0.11 * smoothstep(-0.03, 0.05, elev) * smoothstep(0.3, 0.1, elev)
this.lightDir.y = Math.max(this.lightDir.y + lift, 0.03)
this.lightDir.normalize()
```
- 只作用于 `lightDir`（照地的光 + shader 里的 `uSunDir`）。**日轮走的是 `L.sunDir`**（`EnvironmentManager.ts:160`），不受影响。
- 本项目晨仰角约 12°、暮约 8°（`TimeOfDaySystem.ts:34–37` 注释），正好落在参考页处理的那段低角度区间。按公式（第二个 smoothstep 在 12° 处约 0.44、8° 处约 0.9）算，抬升后大约是晨 15°、暮 14°。
- **风险**：暮景的"低角度暖侧光"是 Phase 2 用户已确认的（`Phase0根因排查报告.md` §7.1）。抬升会略减弱拉长的暖影——只在暮景做 A/B，若效果不喜欢就把 0.11 降到 0.06，或只对晨景开。

#### L-3【P1】阴影按需刷新

**现状**：`RendererManager` 没设 `shadowMap.autoUpdate`，默认每帧重画全部级联。`doc/lighting/README.md` 的实测里阴影通道占 2.4–4.8 ms（衡）。

**参考页**：`autoUpdate=false`，只在光动了、或时钟在走时每 0.1 s 重画（L2486–2489）。

本项目世界大，视锥随镜头动，所以**镜头在动时无法省**；但地图应用里相当一部分时间在读诗、镜头静止。做法：
```ts
// RendererManager：renderer.shadowMap.autoUpdate = false
// ShadowManager.update() 末尾（现在的签名没有 dt，需要从 Engine 传进来）
const moved = this.lastCamMatrix.equals(camera.matrixWorld) === false
const lightMoved = this.lastLight.distanceToSquared(sunDir) > 1e-6
const idleTick = (this.idle += dt) > 0.1            // 静止时 10 Hz 兜底：船、鸟、行人等动态投影体不会冻住
if (moved || lightMoved || this.chunksChanged || idleTick) {
  renderer.shadowMap.needsUpdate = true
  this.idle = 0
  this.lastCamMatrix.copy(camera.matrixWorld); this.lastLight.copy(sunDir)
}
```
- `chunksChanged`：`ChunkManager` 本帧有新区块上传/淡入时置位。
- **不要**做到"完全不刷"：`LifeSystem`（船、行人）与鸟会投影，静止 10 Hz 兜底是安全下限。
- **预期收益**：只在镜头静止时省，≈ 阴影通道耗时的 90%。镜头在动时无变化。**这个数要实测**，不能拿 README 的 2.4–4.8 ms 直接当结论。
- 工作量：30 行，无美术风险。

#### L-4【P1】天空加"太阳方位地平光带"

参考页天空着色器（L2170–2177）在低太阳时沿地平线、**朝太阳方位**加一道暖光带：
```glsl
float low  = smoothstep(0.55, 0.0, uSunDir.y);
float band = smoothstep(0.45, 0.0, abs(h)) * pow(sd, 2.0) * low;   // sd = dot(视线, 太阳方向)
col += uSunCol * band * 0.35 * uSunGlow;
```
本项目暮/晨的地平线颜色是固定三段渐变（`SkySystem.ts:60–71`），**与太阳方位无关**，所以镜头背对夕阳看去的地平线和面向夕阳看去一样亮。加这道光带能给暮景一点方向感，成本是天空 shader 里 4 行。
- 与 `uSkyLift`（俯仰自适应渐变带）不冲突，加在 `col` 上即可；`sd` 要用 `L.sunDir`（真实太阳）。

#### L-5【P2】连续时辰（按高度角插值）

参考页用 `SKY_KEYS`（10 个按 `e` 排序的关键帧）+ `keyLerp` 得到任意时刻的天空色，本项目现有 4 个 `SkyTokens.*` **本身就是关键帧**，可以按太阳高度角排成 `[夜 −0.29, 暮 0.124, 晨 0.197, 昼 0.85]`，再补两三个过渡帧（晨/暮之间的金色时刻）。
- 这是产品决定：现在界面是"晨昼暮夜"四个按钮，连续时辰意味着加一个滑块/自动循环；诗词场景多是"夜泊""暮登"这类**指定时辰**，四档已够用。**建议 P2，且先问产品**。
- 若做：用 `tod ∈ [0,1)` → 太阳轨迹用参考页的 `|sin|^1.6` 曲线（低角度停留久）；`TimeOfDaySystem.apply()` 的线性插值改成按 `e` 查表。

#### L-6【P2】灯光烘焙进顶点 + 依序点亮

参考页的夜景"暖"有两个来源：点光（6 盏，仅宝塔）和**逐方块预烘焙**的 `aLit`（灯笼半径 5.6、窗 4.0 内的方块暖色抬升，二次衰减），加 `uSeq` 让灯**由宝塔向外依次点亮**。
本项目 `world/light/VoxelLight.ts` 已经能算 0–15 级块光，但 README 明确"目前只计算、不参与渲染"。接上的路径：网格器把每个顶点的块光（0–15）打进一个新属性（或塞进 `aAo` 的空位），shader 里 `totalEmissiveRadiance += warm * blockLight/15 * uNight`。
- 这是"夜景屋檐下、灯笼旁的墙面发暖"的成本最低的实现，比点光合适（点光数量受限，参考页也只敢放 6 盏）。
- 注意区块缓存构建号：改网格器属性布局要让缓存失效（`git log` 里 a1e92b8 已把构建号改成源码内容指纹，自动生效）。

#### 已经吻合、不需要改的

- **太阳偏向镜头肩后**：本项目晨/昼/暮方向的 `z` 都是正（偏南），默认镜头在南，等效于参考页"低太阳偏南、从侧面照塔"。
- **远景不投影、地被不投影、树叶只近处投影**：`ShadowManager` 文档注释与参考页 L1876/L2027 一致。
- **AO 与面向明暗只乘间接光**：参考页是顶点色里直接乘（AO）、着色器按法线乘（面向），本项目的"只乘间接光"更严谨，不会与 Lambert 再压一次。

#### 比参考页对比度高的一点（需美术确认）

正午太阳:天光比约 2.5（补光另计；参考页 1.7）、曝光 1.05–1.38（参考页 1.0–1.15）；暮景两边都在 2 上下，差别不大。本项目的阴影更深，"通透感"任务（Phase 0–2）已经在处理，此处只记一笔：**若通透感仍不够，先降太阳:天光比再动色板**——它是比雾更直接的杠杆（Phase 0 已排除雾）。

## 2A. 专题：天空色与光照表现（后期重点优化）

> 这一节是"光照表现"后期优化的工作底稿。§2 讲参考页的光照做法，本节把**天空色、环境光、暮夜过渡、后期调色、夜灯、云**放在一起，给出：数据流地图、色值对照、逐项修改（含初值）、验收办法。
> 色值一律是**起点**，没有在本项目里出过图。本项目走"宣纸青绿"的低饱和路线，不要把参考页的高饱和色直接搬过来。

### 2A.1 先看清一帧的颜色是怎么来的

改天空色之前必须知道：**屏幕上看到的颜色 ≠ `SkyTokens` 里写的色值**。

| 量 | 产生 | 消费 |
|---|---|---|
| `top / mid / horizon` | `SkyTokens.*`，晨昼暮夜四档，切换时线性插值（`TimeOfDaySystem.ts:122`） | 天空着色器（`SkySystem`）；雨雪雾再往上罩色（`EnvironmentManager.ts:146–160`）；`mid` 与 `horizon` 还写进 `uSkyColor/uHorizonColor`，被材质的边缘雾用（`MaterialLibrary.ts:41–44`） |
| `fog` | `SkyTokens.*.fog`，白天再向 `mid` 靠 30% | `FogSystem` |
| `ambientSky / ambientGround / ambientI` | 同上，每档写死 | 半球光 + 对向补光 |
| `sun / sunI / sunDir` | 同上（方向在 `PRESET`） | CSM 平行光；`lightDir` 还进 shader |
| `exposure` | `PRESET` | `toneMappingExposure`（ACES） |
| `night / warm` | 时辰 | `RenderPipeline.setLight()`：泛光、**调色**（分色调、暗角、S 曲线） |
| `cloud` | `SkyTokens.*.cloud`，参与插值 | **没有任何代码读它**（3D 场景里目前没有云物体，见 S-6） |

三个后果：

1. **天空最终色 = token → ACES（曝光 1.05–1.38）→ 调色 → 暗角**。调色里 `uHighTint`（亮部偏暖）在暮景是 `(1.09, 1.02, 0.89)`、强度 0.7：亮部蓝通道约 −8%。按 `#F2C49A` 的暮景地平线算，蓝通道由 154 掉到约 142，红通道被顶到 255——**屏幕上比 token 更橙**。所以调天空色**一律以屏幕取色为准**，不要只看色值。
2. **「轻」档没有调色、泛光与暗角**（`RenderPipeline.setQuality`：`low` 直接 `renderer.render`）。同一组色值在轻档和衡档观感不同。约定：**在「衡」档调，在「轻」档复核**。
3. 环境光和天空**各写各的**：雨雪天只改了天空色（往 `skyRain` 靠），半球光颜色没跟着变，只有强度乘了 `W.light`（`EnvironmentManager.ts:135–137`）。

### 2A.4 逐项修改

#### S-1【P0】暮/晨 ↔ 夜之间加"薄暮"中间帧

**问题**：暮→夜是两档预设做 1.4 s 线性插值。
> **更正（实施时实测）**：原文按 token 十六进制算出"中点 `#AE9E93`、饱和度 14%"是错的——c37c31b 起天空三段写进场景的是反解 ACES 的 HDR 色，夜景曝光也不同。按实际屏幕色，直插中点地平线是 `#D3B2A5`（饱和度 0.34）、中段 `#AD919F`（0.15），是偏粉的暖灰而不是脏米色。本节原先给的中间帧色值（`#C08A88` 等）在屏幕上反而比直插更灰，已改为 `#D4857A / #8E6F9A / #3E4C7E`（地平线屏幕饱和度 0.51）。收益比原先估计的小，属于"过渡更有颜色"的美术改进。参考页在日落后经过红粉 → 紫 → 靛三段（上表 e=−0.02 到 −0.16），天是"烧"过去的。

**改法**：在 `TimeOfDaySystem` 里增加一个**不对外的中间关键帧** `TWILIGHT`，只在 暮/晨 ↔ 夜 的过渡里经过：

```ts
// 1. 把 apply() 里的逐字段插值抽成 blend(a, b, k, out)
// 2. 中间帧：取暮与夜各半，再覆盖颜色（避免维护全部字段）
const TWILIGHT_OVERRIDE = {
  top: '#46567F', mid: '#8A7590', horizon: '#C08A88',   // 起点值，见下表
  fog: '#9A8A94', ambientSky: '#9AA4C4', ambientGround: '#6F5A66', cloud: '#8A7C90',
}
// 3. set()：暮/晨 → 夜、夜 → 暮/晨 时记 via = twilightLook，过渡时长 2.4 s（其余仍 1.4 s）
// 4. apply(k)：via 存在时 k<0.5 用 blend(from, via, 2k)，否则 blend(via, to, 2k−1)
```

**起点值**（由 §2A.2 的参考色按本项目饱和度折算，要出图后调）：

| 位置 | 建议初值 | H / S / L | 说明 |
|---|---|---|---|
| 天顶 | `#46567F` | 223° / 29% / 39% | 介于暮 `#7089AB` 与夜 `#1D2F4A` |
| 中段 | `#8A7590` | 287° / 11% / 51% | 紫调，参考页 e=−0.07 的 `#7a4a78` 淡化 |
| 地平线 | `#C08A88` | 2° / 31% / 64% | 红粉，参考页 `#f0766a` 淡化 |
| 雾 | `#9A8A94` | — | 带进紫调，避免远山在过渡时突然变灰 |
| 环境地面 | `#6F5A66` | 326° / 10% / 39% | 暖紫棕，参考页 `#6d4a66` |

- **不要动**：暮景选定"夕照黄昏、无月"（Phase 2 用户已确认）。中间帧只在**过渡中**出现，稳定的暮景、夜景不变。
- **只影响过渡**这一点是优点：风险小，也不需要重拍暮/夜的验收图；缺点是用户只在切换时看到。如果要让"暮蓝"成为可停留的状态，那是 L-5（连续时辰）的事。

#### S-2【P0，仅色值】地面反光改暖 —— 改动最小、影响最大的一条

**原理（three.js 半球光）**：
`辐照度 = mix(groundColor, skyColor, 0.5 + 0.5·n.y)·intensity`。
**竖直墙面 `n.y = 0`，一半吃天色、一半吃地面色。** 所以 `ambientGround` 决定了**所有背光竖直面的颜色**——墙、崖、塔身的阴影面。

本项目地面色近乎纯灰（S 1–8%），背光墙面就是"冷天光 + 灰" → 单色冷阴影。参考页是"冷天光 + 暖棕地面" → 阴影面上冷下暖、有层次，也是山水画里"石青阴、赭石暖"的关系。

**只改 `palette.ts` 的 `SkyTokens.*.ambientGround`**，初值：

| 档 | 现值 | 建议初值 | 依据 |
|---|---|---|---|
| dawn | `#8E9D92` | `#A09A88` | 暖灰橄榄，保留一点草绿 |
| day | `#90A094` | `#9A9480` | 同上，更暖 |
| dusk | `#8A8D8B` | `#86707A` | 暖紫灰，参考页 `#6d4a66` 淡化 |
| night | `#526170` | 不动 | 夜里保持冷 |

- 这会略降背光面的整体亮度（昼档地面色明度 60% → 约 55%），若通透感受影响，把对应 `ambientI` 补 +0.03–0.05，**一次只动一档**。
- 零代码。回滚只需还原色值。
- 验证：昼 · 庐山机位，看背光崖壁与白墙的阴影面是否"暖了一点、没脏"；用 `tools/lum.mjs grid` 对比亮度不掉。

#### S-3【P1】环境光跟着天空色与天气走

在 `EnvironmentManager.update()` 里，`hemi.color/fill.color` 现在直接取 `L.ambientSky`（`:129, :135`）。改为：

```ts
// 需要把这两行挪到 sky.update 之后（因为要用到已经罩过雨雪雾色的 mid）
const amb = this.tmpAmb.copy(L.ambientSky).lerp(mid, 0.25)
amb.lerp(this.rainSky, rainK * 0.3).lerp(this.snowSky, snowK * 0.3)
this.hemi.color.copy(amb)
this.fill.color.copy(amb)
```
- 效果：雨雪雾天，天变灰青时，阴影里的天光也跟着变，画面统一；现在是天灰了、阴影仍是晴天的蓝。
- 系数 0.25 / 0.3 是起点。注意 `tmpAmb` 需新增一个 `THREE.Color` 成员。

#### S-4【P0】暮景地面直射光其实很弱——低角度光的数学

`平地受光 = sunI · sin(太阳高度角)`：

| 档 | 高度角 | `sunI` | 平地直射 | 抬升 0.11 后 | 平地直射 |
|---|---|---|---|---|---|
| 昼 | 54° | 2.86 | 2.30 | — | — |
| 晨 | 12° | 2.16 | 0.45 | 约 15° | 0.55 |
| 暮 | 8° | 1.94 | **0.27** | 约 14° | 0.46 |

暮景平地的直射光只有正午的 12%，**比 `ambientI`（0.95）小得多**——暮景的地面主要是天光在照，不是夕阳。夕阳只照亮朝西的竖直面（`cos 8° ≈ 0.99`，满强度）。这就是暮景"墙亮地暗、对比生硬"的来源，也是 L-2（主光抬升）的量化依据。

- 抬升后平地直射增加 70%，竖直面几乎不变（`cos 14° = 0.97`）。
- 对照参考页：金色时刻太阳强度是正午的 ≈ 92%（3.3 / 3.6），本项目晨 76%、暮 68%。若 L-2 之后仍觉得暮景发闷，再考虑把 `dusk.sunI` 从 1.94 试到 2.3（**一次只动一个**；这是 Phase 2 已确认的方向的强度微调，不是换方向）。

#### S-5【P0】天空里朝太阳方向的光（= §2.3 的 L-4）

见 L-4。补充一点：这条在暮、晨最有效；本项目暮景已是"日轮 + 一圈晕"，加上朝日的地平光带后，背对夕阳的镜头也能从地平线亮度分布读出太阳方向。在 `SkySystem.ts` 片元着色器里 `col` 算完 `lift` 混色之后、画日轮之前加。

#### S-6【P2】云

**现状**：`SkyTokens.*.cloud` 四档色值已经设计好（晨 `#E4D8C8`、昼 `#D5E2DC`、暮 `#E2C4AE`、夜 `#3C5068`），`TimeOfDaySystem` 也插值了它，**但没有云物体读取**。
**参考页**：体素云（2 格立方体成层，46 团，三个高度：山后主云、远景云、高空丝云），云的光完全由天空色驱动（§2A.2）。云在山水画里是最重要的"留白"和"层次"，也是暮景的主要色彩载体（云底被夕阳染色）。
**做法**：云用一个 `InstancedMesh` + `MeshLambertMaterial`，自发光按 §2A.2 的公式由 `L.horizon/L.top` 算，底色按 `L.cloud`；不投影；离相机近时立方体缩小（`smoothstep(12,55,dist)`，避免飞进云里满屏大方块）；漂移在顶点着色器里由 `uTime` 驱动。
**位置**：全国尺度，云不能只放在一个点周围，要跟着焦点/镜头分块生成（参考 `NightLanterns` 的"逐盏回收"，别整批重撒）。工作量大，P2，但**收益是光照表现里最直观的**——建议在 S-1 到 S-5 之后做。

#### S-7【P1】夜灯：依序点亮 + 灯笼轻微闪烁

- **依序点亮**：参考页黄昏时灯笼**由宝塔向外**依次点亮，6.5 秒扫完（`uSeq` × 每盏灯的延迟 `glowDelay`）。本项目 `uNight` 是全局 0→1（1.4 s），所有灯同时亮。做法：新增 `uLitSeq` uniform，窗光/灯笼的自发光乘 `smoothstep(d, d+0.12, uLitSeq)`，`d = 归一化后的 |世界坐标 − 焦点| / uLitFar`。`MaterialLibrary.ts:251` 已经有 `distance(vBWorld, cameraPosition)` 的 `lit`，改成按焦点距离并加上 `uLitSeq` 即可。
- **灯笼闪烁**：参考页三频叠加 `1 + 0.16·sin(t·(9+1.7i)) + 0.09·sin(t·(23+3.1i)) + 0.05·sin(41t)`。**本项目 `a1e92b8` 提交刚修掉"楼阁灯窗夜里闪"**，所以：**只给灯笼/火把闪，不给窗；振幅 ≤ 6%、频率 ≤ 3 Hz**，否则会被看成回归。
- 两条都依赖 `uNight` 的时序，与 S-1 的"薄暮"过渡配合最好：薄暮期间灯逐盏亮起来。

### 2A.5 后期调色的位置

本项目有**参考页没有的**调色（分色调、S 曲线、暗角、纸纹，`RenderPipeline.ts:18–57`）。光照表现优化里它是一个杠杆，但要注意：

- 暗部偏石青、亮部偏宣纸这套分色调**已经在给阴影加冷、亮部加暖**。S-2（暖地面）会和它叠加：阴影面既被暖地面反光加暖、又被 `uShadowTint (0.94, 0.99, 1.05)` 加冷，部分抵消。验证时留意阴影面是否"变灰"；若变灰，把 `uShadowTint` 的蓝通道从 1.05 降到 1.03，而不是撤回 S-2。
- 暗角 0.34（夜 0.62）压的是画面四角；俯视机位下，天空恰好在上方两角，**天空在角上会比中间暗一截**。看天空色截图时取**画面上部中央**，不要取角。
- `uHighTint` 的暖偏（暮景蓝通道 −8%）是暮景偏橙的另一半原因（§2A.1）。若 S-1/S-2 之后暮景过橙，先降 `warm` 系数，不要改天空 token。

### 2A.6 验收：用屏幕取色，不是用 token

1. **取色表**：固定机位（庐山 `shp=lushan` 与全国 T01）× 晨昼暮夜 × 春夏，在截图上取三个固定位置：天空上部中央、地平线（天与最远山相接处）、一处阴影面（背光崖壁）。记 RGB 与 HSL，写进 `doc/lighting/` 下的表。以后每改一组，对照这张表。
   - `tools/lum.mjs` 现在只有亮度环带/网格。给它加一个 `probe <png> x,y ...` 输出 RGB 即可（约 15 行）；`shoot.mjs` 已能逐场景固定机位出图。
2. **过渡序列**：暮→夜、夜→晨每 0.3 s 一张，共 8 张，看有没有"脏灰"帧（S-1 的验收）。
3. **轻/衡复核**：同一场景两档各一张，天空与阴影不应出现明显色相差（明度差异来自调色，可接受）。
4. **不动的约束**（沿用 Phase 0–2 的结论）：暮景为夕照、无月；月盘位置与尺寸不动；一次只改一组变量；`SkyTokens` 的 top/mid/horizon 昼景已定稿，除非取色表显示问题，不再动。

### 2B.3 结合后真正新增的优化项

#### N-1【P0，需先测量】阴影在镜头距离 ≥ 900 时整体硬关闭

`ShadowManager.update()`：
```ts
const want = this.enabled && distance < 900 && sunDir.y > 0.05     // ShadowManager.ts:136
for (const l of csm.lights) l.castShadow = want
```
> **实施时实测（2026-09-30）**：杭州缩放扫描，920 → 860 整幅平均亮度 **−12%**（165.2 → 145.4），是整条扫描里最大的台阶。
> 根因比下文推断的更严重：同机位（860）只改阴影参数——`shadow.intensity` 1 → 0 亮度 144.0 → 144.1（阴影本身几乎不影响均值），**`castShadow` 关掉 → 163.0**。
> 原因在 three 的 `CSMShader.js`：没有投影的平行光走"compute the lights not casting shadows"循环，**每一盏级联灯都按满强度照一遍**；
> 而 `ShadowManager` 把每盏级联灯的强度都设成太阳强度。于是镜头过 900（或光线低于 `y=0.05`）时**太阳按级联数叠加：衡两倍、高三倍**。
> 这才是"中距离 / 全国层发白"的真正来源——不是曝光，也不只是阴影消失。已修：开着阴影时级联灯始终投影，只把 `shadow.intensity` 随距离（600→900）与光线高度淡出。

`distance` 是镜头到注视点的距离。缩放拉到 900 的一瞬间，**所有阴影同时消失**：山体背光面、树荫、建筑投影全部被太阳"直接照亮"，整幅画面有一次亮度台阶。这比"曝光随相机变"更像那篇描述的"中距离层突然发白"的真实来源——曝光没变，是**遮挡没了**。

- 相邻的还有：级联最远距离 `maxFar = clamp(distance·2.6+150, 250, 700)`，距离 ≥ 212 后固定 700（按视锥深度算）；镜头距离超过 700 后，注视点（画面中心，深度 = D）就**落在阴影范围之外**，只剩镜头近处有阴影。所以 700–900 之间已经是"半有半无"，900 再整体关闭。
- **改法（先量再改）**：用 N-3 的缩放扫描测 900 前后亮度。若台阶明显：不要用 `castShadow` 开关，改成随距离衰减阴影强度（three r186 的 `light.shadow.intensity`，**需确认 CSM 的自定义着色片段是否读它**；不读的话，退路是把开关点推到 1300 以上，与 `national` 级别切换同一处，让两个变化合并成一次）。
- 这是 §2.3 L-3（阴影按需刷新）的前置：同一个文件、同一处逻辑，一起改。

#### N-2【P0】间接光的三重遮蔽设下限；烘焙贴图边缘羽化

**乘积没有下限**（`MaterialLibrary.ts:266`）：
```glsl
reflectedLight.indirectDiffuse *= bakedSky(vBWorld) * aoCurve(vAo) * faceShade(vBNormal);
```
最坏情况（院落里的南北向墙面）：`bakedSky 0.55 × aoCurve 0.80 × faceShade 0.88 ≈ 0.39`，高画质再叠 GTAO（0.14 混合）。阴影里的墙面只剩天光的约 39%——这就是"地标周围院落、檐下死黑"的一个来源，Phase 0 报告 §2 已把它列为"三重遮蔽叠加"风险，但还没有修。
```glsl
float occl = bakedSky(vBWorld) * aoCurve(vAo) * faceShade(vBNormal);
reflectedLight.indirectDiffuse *= max(occl, 0.55);   // 下限起点 0.55，出图后调
```
- 下限是**保护背光面可读性**，不改正常表面（正常表面乘积多在 0.8 以上）。

**烘焙贴图边缘是硬边**（`bakedSky()`，`MaterialLibrary.ts:85–90`）：范围外直接返回 1.0，而贴图内边缘像素可以低到 0.55（山坳、院落在烘焙区边缘时），于是烘焙区边缘出现一圈**亮度台阶**（离地标约 80 格）。
```glsl
float bakedSky(vec3 w) {
  if (uBakeRect.z < 1.0) return 1.0;
  vec2 uv = (w.xz - uBakeRect.xy) / uBakeRect.zw;
  if (uv.x < 0.0 || uv.y < 0.0 || uv.x > 1.0 || uv.y > 1.0) return 1.0;
  vec2 e = min(uv, 1.0 - uv);
  float k = smoothstep(0.0, 0.12, min(e.x, e.y));       // 外沿 12% 渐入
  return mix(1.0, texture2D(uBakeMap, uv).r, k);
}
```
- 验证：庐山、长安这类有烘焙的地标，绕行观察烘焙区边界（`shp=` + 地面机位 + 亮度网格）。

#### N-3【P0，验收工具】缩放扫描：全国 → 区域 → 地面的亮度稳定性

那篇里最值得直接采用的一条：**做一个自动化的连续缩放序列，检查每一级过渡有没有亮度台阶。** 本项目所有"层"的切换点都是具体数字，正好可以逐个点测：

| 距离 D | 会变化的东西 |
|---|---|
| >1500 | 近景区块全部收起（`radiusFor` 返回 0） |
| 1300 / 1150 | national ↔ regional 级别切换 |
| 900 | **阴影整体关闭**（N-1） |
| 520 | 近景半径开始收缩 |
| 285 / 240 | regional ↔ local |
| 各半径边界 | 近景 → 2× → 4× → 覆盖图 的掩膜让位 |

**做法**：固定注视点（庐山、长安各一）、固定 yaw/pitch，D 依次取 `[3000, 2000, 1400, 1100, 900, 700, 500, 350, 260, 200, 140, 90, 60, 35]`，每级等区块载完后截图，用 `tools/lum.mjs grid` 取 8×5 网格平均亮度与三个固定探针（§2A.6），列成一张表，**相邻两级平均亮度变化 > 6% 就标红**（阈值是我的起点，可调）。
- `shoot.mjs` 的 `setup` 支持表达式数组、每项后自动等区块载完；改 `__shanhe.engine.camera.goal.distance` 后需多等约 2 秒（距离阻尼 `4.5/s`）。若要绕开阻尼，用工作区新增的 `setFixed(eye, look, fov)`。
- **这张表应该在做任何光照改动之前先跑一次**，作为 baseline；此后每改一组都回归。它比"看起来是否统一"可靠。

#### N-4【P1，实验】补光比例试到 0.15 左右

那篇的核心论证成立：**提曝光会同时抬白墙、天空、水、远雾；补光只抬没被太阳照到的面。** 本项目补光是**直射光路径**（`DirectionalLight`），**不被 AO / 烘焙 / 面向系数衰减**（那三个只乘 `indirectDiffuse`），所以它是最干净的"抬暗面"杠杆。现状 0.11（相对太阳）略低于那篇的 0.12–0.22。
- 实验：昼档补光 `0.32 → 0.40`（约 0.14），同机位前后各一张，看崖壁背光面、树冠背面、黑瓦是否抬起来且**天空/水面亮度不变**。
- 与 N-2（下限）二选一优先：N-2 只修"被三重遮蔽压到 0.39"的极端区，N-4 是全局抬暗面；建议先 N-2，再视效果决定是否需要 N-4。
- 注意：补光位置在 `focus − lightDir·400`、高 300（`EnvironmentManager.ts:131`），方向基本固定；抬得太多会让阴影面"平"。

#### N-5【P1】夜间：先试降曝光，别靠曝光救

本项目夜的 `exposure` 是 **1.38**（昼 1.08），`ambientI` 1.02（昼 1.14），补光 0.52。也就是夜里环境光几乎和白天一样强、再乘更高的曝光。这与那篇"暗部靠补光救、不靠提曝光"的原则相反，也是夜景"没层次"的一个候选原因（月光主光 1.3 对环境 1.02，对比只有 1.3 倍）。
- 那篇给的"夜 0.88"是另一个项目的数，**不要照抄**。
- 实验：夜 `exposure 1.38 → 1.15`、`ambientI 1.02 → 0.85`，同机位前后各一张，看月光面/背光面/灯窗的层次是否拉开，同时确认水面银鳞与灯笼泛光没被压死。注意泛光阈值随夜改变（`RenderPipeline.setLight`：`threshold = 1.3 − 0.33·night`），曝光降了泛光会变弱，可能要同步降阈值。
- 一次只动一个量：先曝光，再环境光。

#### N-6【P1】若要加局部点光：数量固定，别开关

那篇建议"每个亭/塔 1–3 盏共享点光，不要每个窗户一盏"，与参考页做法一致，与 §2A S-7 也一致。落地时有一个容易踩的坑：**three.js 里光源数量变化会让所有受光材质重新编译**（灯数写进着色器）。本项目材质已被 CSM 和 `onBeforeCompile` 打过补丁，重编译成本更高，并且会在切换时卡顿。
- 参考页的做法：`renderer.compile()` 在启动时把"灯开"和"灯关"两种都预热一遍（L2737–2740）。
- 本项目建议：**固定 3 盏点光始终在场景里**，白天强度 0（不改 `visible`），夜里按最近的地标搬位置、拉强度。这样灯数恒定，不触发重编译。

#### N-7【P2】回归护栏

那篇的原则"曝光只由时段决定"目前靠人记住。加一条 vitest：对 `EnvironmentManager.update()` 用不同 `distance / focus.y / 相机高度` 调用，断言 `toneMappingExposure` 不变。10 行，防止以后有人给"近景太暗"加个按距离的曝光补偿——那是三层曝光问题的老根。

## 3. 山体系统

### 3.1 参考页的做法

**高度函数**（L313–347，`macroHeight(x,z,T)`）是**解析构图**，不是纯噪声：

| 层 | 公式要点 | 作用 |
|---|---|---|
| 城坡 / 高地 | 城坡 `PH − step − 0.33·(z−…)`；高地台地 `PH + rise + lateral + ridge`，用 `smooth(zc+ew, zc−ew, z)` 混合成陡崖 | 山下城、山上塔的台阶式构图 |
| 侧山 | `sideW·(14 + 34·smooth(−70,130,−z))`，谷两侧渐高 | 山谷"合围" |
| 主峰 | **9 座高斯峰** `h += A·exp(−r²/2σ²)`，振幅 30–90、σ 22–70，位置随种子抖动；其中一座**负振幅 −40**（凹口/鞍部） | 读得出来的峰形，而不是一片起伏 |
| 山脉纹理 | `52 · mask · (ridged(x·0.013, z·0.013, 5 倍频) − 0.36)`，`ridged` 里 `r = 1−|n|; r *= r` | 山脊线清楚、山谷圆 |
| 低频起伏 | `5·fbm(0.021) + 1.8·fbm(0.09)`，被位置遮罩 | 近景不平板 |
| **软上限** | `if (h > 118) h = 118 + (h−118)·0.72` | 近景网格不撞天花板，远山仍高耸 |

**关键点**：`macroHeight` 不含方块级细节，**近景网格和远景环共用它**，所以近远交界没有高度差。

**上色**（L787–796，`biome()`；L1706，`voxelColor()`）：
- 雪线 `86 + SITE.snow + 9·patch`，高山草甸线 `66 + 7·patch`，都带低频噪声——**雪线是曲线不是一刀切**。
- 坡度 ≥3（相邻格高差）直接露岩，雪线以上坡度 ≥2 且噪声>0.12 也露岩——**雪只留在缓坡上**。
- 岩石：`floor((y + 3.5·patch)/2.4)` 取 9 种岩色之一，**沉积层带**。
- 每个方块 `k = 0.93 + 0.14·hash`（岩石 0.88–1.10），草地按大块噪声在三种绿之间混。

**构图**：镜头方位限制在 ±1.9 弧度（约 109°）（L2385–2389），理由源码写得很直白："宝塔山脉背面只有岩石可看"——**用户永远在山谷一侧，山永远在地标背后当背景**。

### 3.2 本项目现状

`TerrainManager.column()`（`TerrainManager.ts:79–215`）流水线：宏观高度（真实地理 DEM 锚点）→ 方块级细节 → 海岸 → 江河 → 湖泊 → 地标修改器。

- **细节**：`fbm(x/52, 3 倍频)` 与 `ridged(x/96, 3 倍频) − 0.45`，幅度 `min(24, 0.7 + relief·0.95)`，名山主峰附近收敛（`damp`）。
- **台层**：`relief>5` 的山地按 **7 格一级**做出台阶（权重最高 0.3）。
- **区域地貌**：喀斯特峰林、黄土沟壑与梯田、沙漠新月丘。
- **上色**：`resolveBiome`（纬度、海拔、坡度、噪声）；`biome === Snow && slope > 2.2 → 顶面露岩`（`TerrainManager.ts:379`）——"雪只留在缓坡"这条**本项目已有**。
- **陡壁岩层带**：shader 里每 6 格一层岩带、台面亮层缝暗（`MaterialLibrary.ts:214–229`），与参考页的沉积层带同一思路。
- **高度映射**：`Y = 41 + 44·(千米)^0.78`（`WorldConfig.ts:38–41`），珠峰 ≈ 280，本身就是一个压缩曲线，等价于参考页的"软上限"；`clamp(…, 1, 300)`（`TerrainManager.ts:213`）几乎咬不到。

### 3.3 差异与可借鉴点

**总体判断**：本项目的山体生成是**数据驱动**的（真实地理 + 名山锚点），参考页是**构图驱动**的（为一个视角摆好山）。二者目标不同，生成部分**不建议改**。真正值得借的是"山怎么被看见"：

#### M-1【P0】远景雪色偏冷、远景凹处压暗（对应 Phase 0 候选 1）

Phase 0 报告把"白色阶梯状背景山形"的头号候选归因于**雪盖 + 体素列量化**（`Phase0根因排查报告.md` §3 候选 1）。参考页对同一问题的处理是三件互相配合的小事：

1. **远景雪色偏冷灰蓝**（L1893、1938）：
   ```js
   FAR_SNOW = 0x93a7c8                          // "so it never reads as cloud"
   tint = min(0.7, 0.2 + S * 0.03)              // S = 该环方块边长；2→0.26，4→0.32，8→0.44，24→0.7
   if (mt === SNOW) col.lerp(FAR_SNOW, tint).multiplyScalar(0.92)
   ```
2. **远景方块凹处压暗**（L1936）：`ao = 1 − 0.06·higher`，`higher` = 四邻里比自己高的个数。廉价的"谷底暗一点"，让远处台阶有体积而不是一片白。
3. **雪只在缓坡**：本项目已有（见 §3.2），但只在**近景网格器**里；远景片（`CoarseGenerator`）用的是 `s.topBlock`，来自 `finish()` 同一处，所以**其实也吃到了**。覆盖图（全国代理）另算，需要核对。

**在本项目落点**：
- `MaterialLibrary.createBlockMaterial(kind, tier)`，`tier !== 'near'` 时，在 `#include <map_fragment>` 之后对**雪块的顶面**（用 tile id 判断，与 `MaterialLibrary.ts:216` 的岩块判断同法）：
  ```glsl
  // tierTint: near 0 / far 0.26 / coarse 0.32（新增 uniform 或编译期常量）
  col = mix(col, vec3(0.58, 0.66, 0.78) /* ≈ 0x93a7c8 转线性 */, tierTint);
  col *= 0.92;
  ```
- 远景凹处压暗：`CoarseGenerator` 已经在算每格的 `top`，比较四邻 `top`，`higher` 个数写进 `vol.biome` 旁的一个通道，或直接在网格器里把 `aAo` 设成 2（`aoCurve` 0.95）。**需要看 `VoxelMesher` 的远景路径是否给顶点写了 AO**（我没读到这里，标注为待核实）。
- 同一件事在覆盖图 `OverviewRenderer` 的材质里也要做，否则近远交界会出现台阶。
- **验证**：Phase 0 的固定机位 T01/T02，`世界无雾`视图 + `只远景`视图前后各一张（`Phase0…报告` §3b 已建立这套对照）。

#### M-2【P1】远景片顶高：先平滑再量化

**现状**：`CoarseGenerator` 每 4 格取**一个点**（`terrain.lattice(x0−C, z0−C, W, C)` 取格中心），再 `Math.round((surfaceY+1)/C) − 1` 量化。
对比：覆盖图 `OverviewBuilder.ts:73` 已经"每格取四个象限点的平均高度"；参考页远景环用 `sm = (4·h + 四邻)/8` 的轻度平滑，注释"轻度平滑让远处山脊安静"（L1907）。

单点取样把方块级高频细节（`bump` 14 格、`fbm` 52 格）混叠成参差，量化后每 4 格一级，远脊就成了参差的阶梯。

**改法**：`lattice()` 已返回带外边的 `cols`（`W = n+2`），在 `CoarseGenerator.ts:40` 处：
```ts
const h = (k: number) => cols[k].height
const sm = (4 * h(k) + h(k - 1) + h(k + 1) + h(k - W) + h(k + W)) / 8   // k = (j+1)*W + (i+1)，与 lattice 内部同索引
const top = Math.max(0, Math.round((sm + 1) / C) - 1)
```
- **风险**：峰顶会被削低（几格量级）。2× 远景（`downsample2`，来自真实体素）与 4× 远景片交界靠 `maskDiscard` 让位——远景片比 2× 低的地方，2× 直接盖住，不会露洞；比 2× 高的地方，远景片在被 2× 覆盖的区域会被 discard，也不会穿出。但**名山峰顶**要盯：`TerrainManager.peaks` 专门让峰高落在校准值上，平滑可能让 4× 层峰顶比 1×/2× 层低一档，近远切换时山尖"缩一下"。建议**对靠近名山锚点的格子关掉平滑**，或先看效果。
- 水面 `waterY` 不要参与平滑。

#### M-3【不建议】程序化构图 / 高斯峰 / 软上限

- 高斯峰构图是为"山永远在塔背后"的一个固定视角服务的。本项目山来自真实地理，改成高斯峰会丢掉名山的真实位置。
- 软上限：本项目已经用幂函数压缩，`clamp(…,1,300)` 咬不到，**不需要**。
- 山脉纹理 `ridged²`：本项目 `ridged` 的具体形状我没读（`utils/noise`），若山脊线不够利，可以试 `r = 1−|n|; r *= r` 这一句，但没有证据说明现在不够利，**不建议先动**。

## 4. 镜头高度与避地

### 4.1 参考页的做法

**控制器**（L2339–2341）：OrbitControls，`minDistance 12 / maxDistance 320`（世界 256 格宽），极角 `0.06 → 0.56π`（**允许略向上看**，相机可低于目标），阻尼 0.07。`fov 50`，竖屏（宽高比 <0.8）`fov 62`（L2724）。近远裁剪面**固定** `0.8 / 4000`。

**平移与相机盒**（L2390、2421–2424）：
- 平移目标限制在 `±(OFF−8)`，`y ∈ [0,150]`；相机位置限制在 `±(OFF+160)`（即可以站在世界外 160 格）。
- **缩远时不推着枢轴走**（L2410–2418）：按相机盒剩余空间动态收 `maxDistance`，相机停在盒边而不是把枢轴顶出去。

**离地净空**（L2391–2430，最值得看）：
```js
CLEAR_MARGIN = 3, CLEAR_SLOPE = 0.55, CLEAR_NEAR = 2
探针 = 相机周围 5×5 格 + 半径 6/14/30/60 各 8 个方向
need = max over 探针 [ groundAt(p+o) + 3 − 0.55·max(0, d−2) ]
lift = max(0, need − p.y);  p.y += lift
```
- **远处的山脊/斜坡提前、平缓地抬相机**：半径越大要求的净空越低（斜率 0.55），一个前方 60 格的山脊只会把相机抬一点点。
- `groundAt` 含**树、建筑**（`TOP` 数组）和**远景环方块顶**；远景粗方块额外加 `(farS−1)·2` 净空："粗方块绝不能充满镜头"（L1966）。
- **抬升量和用户姿态分开存**（`lift`）：下一帧交给 OrbitControls 之前**先减掉**，否则"蹭一下地形"会被误认成用户自己的操作，视角一点点被棘轮式推高推远（L2399–2400 注释）。

**开场取景**（L2347–2377）：`fitRadius()` 是闭式解——给定目标、方向、一组关键点（塔顶、塔基、城中心、湖），直接算出能装下它们的最小相机距离。开场从塔的近景横扫到**低俯角（0.27 弧度 ≈ 15°）的远眺**，最终画面里山层层退远到天边。

### 4.3 差异与可借鉴点

**先说结论**：本项目的避地机制（`CollisionResolver`）在设计上**已经等价甚至更稳**——平滑、回落迟滞、抬升不入用户姿态、只看地形（区块载入前后一致）。文件头注释记录了旧做法的问题（遇山就抬俯角做遮挡修正，"用户往下压、它往上顶"），现在已换掉。**不建议改机制**，只补三处：

#### C-1【P0】竖屏加宽视场角

参考页：`camera.fov = w/h < 0.8 ? 62 : 50`。本项目 fov 固定 42，`setAspect` 只调 `aspect`。竖屏比 0.5 时水平视场角只有 `2·atan(tan21°·0.5) ≈ 22°`，比一支长焦镜头还窄。
```ts
// CameraController.ts
private readonly baseFov = 42
setAspect(aspect: number): void {
  this.camera.aspect = aspect
  const fov = aspect < 0.8 ? 42 + (62 - 42) * Math.min(1, (0.8 - aspect) / 0.3) : this.baseFov   // 0.8→42，0.5→62，平滑过渡
  if (!this.fixed) this.camera.fov = fov
  this.camera.updateProjectionMatrix()
}
```
- `setFixed` 自带 fov，`clearFixed` 会恢复 `baseFov`——竖屏下应恢复成上面算出的值；改一下 `clearFixed`。
- `CameraDesigner.ts:22` 有一份 `FOV = 42` 常量用于算取景距离，竖屏时应传入实际 fov（或宽高比），否则竖屏下地标装不进画面。**这是需要一起改的点**。
- 项目有 `QualityManager` 的触屏判定（默认「轻」），说明竖屏手机是要支持的目标。

#### C-2【P1】远景粗方块的净空

参考页：脚下是粗方块时，净空额外加 `(farS−1)·2`（L1966）。
本项目：`CollisionResolver` 用的是**真实地形高度**，但显示的可能是 2× 或 4× 远景方块——`CoarseGenerator` 的顶高量化是 `round((surfaceY+1)/C) − 1`，**最多比真实地形高出约 C/2**（4× 层约 2 格），再叠 2× 层的错位。净空 `2.5 + 0.02d`：d=60 时 3.7、d=300 时 8.5，一般够；但**低俯角贴着远景层的山脊**时（d 小、视线扫过 2×/4× 层）净空可能不够。
- 若截图里出现"低机位看山脊，近平面切进粗方块"，再做；做法：`CollisionResolver.resolve()` 里对 `pos` 所在格的**当前显示层级**（`ChunkManager` 有 `maskAt(cx,cz)`，255 近景/192 远景/128 远景片）加 `(cell−1)·2`。
- **没有证据现在有问题**，列 P1 是因为参考页专门为它写了一行，说明踩过。

#### C-3【P1】取景设计：加"天际线"评分与低俯角远眺机位

**现状**：`designCamera` 的俯角只挑 `0.56 / 0.66 / 0.78`（32°–45°），评分里**没有"背景"一项**。所以地标镜头永远是"从上往下看城"，看不到地标背后的层叠远山——而参考页最终画面（俯角 15°）的美恰恰来自那一层层退远的山。

**改法**（两部分）：
1. `CameraDesigner` 评分加第 7 项 **天际线**：沿"从相机看向目标的方向"再往前 150–900 格，每 50 格取一次 `ground()`，算最高的仰角 `atan((g − cy)/dist)`：
   ```ts
   /* 7. 远山背景：视线尽头有 4°–14° 的山脊加分（层叠远山），全无或压顶扣分 */
   let ridge = -Infinity
   for (let dist = 150; dist <= 900; dist += 50) {
     const hd = Math.hypot(tx - cx, tz - cz)                                                       // 水平距离（不是 d）
     const px = cx + ((tx - cx) / hd) * (hd + dist), pz = cz + ((tz - cz) / hd) * (hd + dist)      // 视线水平延长线
     ridge = Math.max(ridge, Math.atan2(ground(px, pz) - cy, hd + dist))
   }
   const deg = ridge * 180 / Math.PI
   score += deg >= 4 && deg <= 14 ? 6 : deg > 14 ? -4 : 0
   ```
   （权重 6 与"前景有水 ≤12"、"偏南 −5·|Δyaw|"同量级，不会压倒视线遮挡的 −30。）
2. 新增**"远眺"机位**：`shot` 参数目前只乘距离（`FocusController.poseFor`，`CameraController.focusLandmark` 的 `shot`），可以再定义一个固定的 `vista` 姿态：`pitch 0.27–0.35`、`distance = base × 2.2–3`，目标略向背景方向偏（参考页 `txB` 把目标放在塔与城之间）。
   - 若要"装下多个点"（地标 + 邻近江湖 + 背景峰），照搬 `fitRadius` 闭式解：对每个点求 `|横向偏移| / (mx·tan(fov/2)·aspect) + 沿视线深度` 与 `|竖向偏移| / (my·tan(fov/2)) + 深度` 的最大值，`mx/my` 是画面留白（参考页 0.86 / 0.845）。约 20 行，无依赖。

#### 不建议照搬

- **方位限制**：参考页限制 ±109° 是因为山背面全是岩石。本项目是自由地图，山两侧都有诗。**不做**。
- **探针 `lift` 提相机 Y（而不是抬俯角）**：本项目刻意选择抬俯角、只看地形，理由在 `CollisionResolver` 文件头（旧做法会忽开忽关）。参考页含树屋顶的 `TOP` 在平移中会"跳"，本项目刻意避免。**保持现状**。
- **固定 near/far**：本项目随距离缩放更合理（世界大 100 倍）。

## 5. 远景控制

### 5.1 参考页的做法：四圈方块环

`RINGS = [[2, 96, OFF], [4, 88, 192], [8, 84, 352], [24, 66, 672]]`（L1890），格式 `[方块边长, 半宽(格), 洞半宽]`，洞 = 内一圈的外沿。

| 环 | 边长 | 覆盖范围（世界坐标，中心原点） |
|---|---|---|
| 细网格 | 1 | ±128 |
| 环 1 | 2 | ±128 → ±192 |
| 环 2 | 4 | ±192 → ±352 |
| 环 3 | 8 | ±352 → ±672 |
| 环 4 | 24 | ±672 → ±1584 |

**保证近远无缝的四个细节**（L1895–1945）：
1. 高度全部来自 `macroHeight()`，无细节噪声，环与环之间是**同一个函数的不同采样密度**。
2. 颜色：顶面用同一个 `biome()` 与 `voxelColor()`，非顶面一律 `ROCK`（层带岩色）。
3. 平滑：`sm = (4h + 四邻)/8`（L1907）。
4. **裙边**：每列方块只从"自己与四邻最低的那一层"填到顶（L1915–1925），环外邻居用该处真实 `macroHeight`——环的外沿既不是一堵墙也不是一条岩色带。去掉朝下的面（`FAR_CUBE` 10 个三角形而不是 12）。

**雾**（L1572、1593–1595、2299）：`FogExp2`，密度 0.0016–0.0021，`f = 1 − exp(−(ρ·d)²)`——

| 距离 | 密度 0.0016（正午） | 密度 0.0021（上午） |
|---|---|---|
| 200 | 10% | 16% |
| 400 | 34% | 51% |
| 700 | 72% | 89% |
| 1000 | 92% | 99% |

加一项**谷地山岚**：`pool = exp(−max(y−26,0)·0.075)·uMist·(1−exp(−depth·0.014))`，与雾合成 `fogF + pool·(1−fogF)`。

结果：环 3（352–672）约 27%–68% 入雾（密度 0.0016），环 4（>672）从 68% 一路到接近 100%，几乎是天空色的剪影——**远山靠雾分层**，颜色本身不做去饱和。

**阴影**：远景一律不投影。**画质天梯**（L2747）：`dpr / 光球 / 阴影图` 三个旋钮，降档必须证明提速。

### 5.2 本项目现状

| 项 | 本项目 |
|---|---|
| LOD | 近景 1×（区块 16）→ 远景 2×2×2（每片 2×2 区块）→ 远景片 4×4×4（每片 8×8 区块）→ 全国覆盖图（8 格一列） |
| 半径（衡） | 近景 `radiusFor(d)`：`max(4, min(13 − shrink, round(d/25.6)+4))` 区块，>1500 为 0；远景 = 近景×1.8；远景片 60 区块 = 960 格 |

| 雾 | 线性 `near=(2.8D+250)k`、`far=(7.5D+700)√k`；再叠**灰化空气透视**（`uMistNear·1.3 → ·4+260`，0.42 强度）、**谷地山岚**、**边缘雾图** |

### 5.3 差异与可借鉴点

#### F-1 远景的颜色一致性——本项目的未提交修改方向正确

`MaterialLibrary.ts` 的未提交修改把"按 LOD 层级去饱和"换成"按像素到镜头的**世界距离**统一做空气透视"，注释写得很明白："与区块层级无关，所以层与层的交界上不会有亮度 / 饱和度的台阶。"
这**正是参考页的做法**（远景环不去饱和、靠雾分层；颜色来自同一个调色板）。Phase 0 报告 §2 把"远景疑似偏灰的第一嫌疑人"指向那段去饱和，这条修改与它吻合。
- **建议**：这条改动可以放心提交，验证用 Phase 0 的"只远景"视图（`shl=`）看近远交界有没有台阶。

#### F-2【P1】雾的形状：线性 vs 指数²，近处有没有一点"氛围"

参考页 `exp²` 从 0 开始平滑起（200 格已有 10%，是一层几乎看不出但存在的空气），本项目**线性雾在 `near = 2.8D + 250` 之前完全为零**——D=60 的近景就是 418 格内无雾。近景圈半径只有 6 区块 = 96 格（`radiusFor(60)`），其外 96–176 格是 2× 远景、176 格以外是 4× 远景片，而线性雾要到 418 格才开始——**这一整段方块颗粒感没有任何雾遮**。
本项目额外加的灰化空气透视 `smoothstep(uMistNear·1.3, uMistNear·4+260, d)`（D=60 时 78 → 500）**恰好补的就是这一段**，所以现状其实与参考页效果接近，只是分两层实现。
- **不建议改雾函数**。若 A/B 后觉得 96–200 格的 2× 层"脆"，把灰化空气透视的起点从 `1.3·uMistNear` 降到 `0.9·uMistNear`。

#### F-3【P1，需美术拍板】天空地平线、雾色、远山的衔接

参考页：`scene.background = fog.color = 天空地平线色`——地平线没有接缝，远山融入天空。
本项目：**刻意分开**。`FogSystem` 文件头注释："颜色用时段雾色，和天空地平线分开，避免远山和天连成一块。" 同时 `SkySystem` 的 `skirt` 是 `mix(mid,horizon,0.45)·0.7`（**比 mid/horizon 都暗 30%**），雾色是 `L.fog` 再向 `mid` 靠 30%。三者不是同一个颜色。

这是一个**风格决策**，不是 bug：
- **A. 融入**（参考页）：雾色 = 天空地平线色，`skirt` 收敛到雾色。远山剪影淡入天空，山水画的"云山"感更强；风险是 Phase 0 排查过的"白色阶梯状山形"会更融进天空而不是显形——反而可能好看，也可能连山形一起吃掉。
- **B. 分开**（现状）：地平线有一条清晰的带，远山有轮廓；代价是俯视机位下"天空裙"和雾色不一致时出现色带。
- **中间路线**：保持分开，但把 `skirt` 的 `·0.7` 去掉，并让 `skirt` 向雾色而不是向 `mid` 靠 40%。只动 `SkySystem.ts:68` 一行。

**建议**：先做中间路线（1 行，可逆），看同机位截图；A 需要用户看了对比再定。

#### F-4【P1】远景片的"裙边"与外沿

参考页每列方块从"最低的邻居"填到顶、外沿用真实高度，所以**环边不是墙**。本项目 `CoarseGenerator` 每列从 0 填到 `top`（`y = 0…top`），交界靠掩膜让位，不是靠裙边，所以问题不同：**远景片外沿到全国覆盖图之间**是否有墙/色带，我没有读到覆盖图的交界处理（`OverviewRenderer.update()` 没读），列为待核实。
- 若 `chunkRadius` 外 960 格处出现一道"矮墙"，参考页的做法是：环外邻居的高度用该点真实 `macroHeight`。本项目对应做法是：`generateCoarseRegion` 生成外边一圈（已有 `W = N+2`），保证外边样本用的是真实地形而非 0。**`lattice()` 已经含外边一圈，理论上已满足**——只需截图确认。

#### F-5【P2】自适应画质

参考页调速器（L2742–2811）值得看：
- 先测显示器刷新率（前 60 帧间隔中位数，`snapHz` 吸附到 48/50/60/72/75/90/100/120/144/165/240），**所有阈值都是刷新率的比例**。
- 连续 3 个窗口低于 80% 刷新率才降档（低于 50% 只要 2 个窗口、一次降两档）。
- **每降一档都要证明有效**：下一个完整窗口帧率 <上一窗口的 1.1 倍，就**撤销这次降档**并锁定（"被浏览器或系统锁在 30 fps 的设备，缩小画布没有用"）。
- 连续够快才一档一档爬回去，每次失败后等待时间翻倍（10→80 窗口）。
- 自动跳过"在这块屏上没有实际差别"的档（1× 屏上 dpr 1.25/1.5/2 是同一档）。

本项目 `QualityManager` 是**静态预设**（触屏 → 轻，其余 → 衡），`doc/lighting/README.md` 的实测有 ±15% 波动，不同机器差别大。可以把 `pixelRatio / shadowSize / shadowCascades / chunkRadius / coarseRadius` 排成一条天梯，接一个类似的调速器。
- 工作量约 120 行，主要是天梯设计（哪个旋钮先降）。**降档的顺序建议**：阴影级联数 → 阴影图边长 → 像素比 → `coarseRadius` → `chunkRadius`（最后动区块半径，因为会改变画面构成）。
- 这不是画质问题，是"低端机不至于卡死"的问题，优先级 P2。
